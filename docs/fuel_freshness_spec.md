## 0. Οι αποφάσεις που κλείδωσαν

1. **Κριτήριο εγκυρότητας = η ΕΒΔΟΜΑΔΑ, όχι οι ώρες.** Η τιμή είναι έγκυρη αν
   η εβδομάδα της περιέχει τη σημερινή ημερομηνία. 40 ωρών αλλά σωστής
   εβδομάδας → **έγκυρη**. 2 ωρών αλλά περασμένης → **άκυρη**.
2. **Άκυρη ή fallback → έντονη προειδοποίηση στην οθόνη, ΧΩΡΙΣ μπλοκάρισμα.**
   Η προσφορά ήδη δηλώνει ότι ο επίναυλος μεταβάλλεται εβδομαδιαία.
3. **Το snapshot προσφοράς αποθηκεύει ΚΑΙ `fetched_at`.**
4. **Τα fallback 47.0 / 35.25 σημαδεύονται ρητά** και ενεργοποιούν την
   προειδοποίηση.
5. **Η προειδοποίηση ΜΟΝΟ στην οθόνη, ΠΟΤΕ στο PDF.**

Ό,τι ακολουθεί υπηρετεί αυτές τις πέντε και τίποτα άλλο.

## 1. Γιατί η εβδομάδα και όχι οι ώρες

Ο επίναυλος αλλάζει **κάθε Δευτέρα** (R13). Ένα TTL σε ώρες απαντά σε λάθος
ερώτηση: στις 23:00 Κυριακής ένα αρχείο 20 ωρών είναι απολύτως σωστό, ενώ στις
00:30 Δευτέρας το ίδιο αρχείο είναι λάθος. Το μόνο κριτήριο που δεν αστοχεί σε
καμία από τις δύο κατευθύνσεις είναι η ταύτιση της εβδομάδας με τη σημερινή
ημερομηνία.

Συνέπεια που πρέπει να ειπωθεί ρητά: **ο έλεγχος τρέχει σε κάθε χρήση, όχι μία
φορά στη φόρτωση.** Μια καρτέλα ανοιχτή από Παρασκευή σε Δευτέρα πρωί πρέπει να
γίνει κόκκινη χωρίς refresh, όταν ο χρήστης πατήσει «Draft» ή «Αποστολή».

## 2. (α) Η ετικέτα εβδομάδας — διαβάζεται αξιόπιστα;

### Τι έχουμε σήμερα

Η ετικέτα είναι **κείμενο ξυσμένο αυτούσιο από τη DHL**
(`poc/fetch_fuel_surcharge.py:101,105`), και αποθηκεύεται ως έχει:

```
"Σεπτέμβριος 21-27, 2026"              ← ίδιος μήνας
"Σεπτέμβριος 28-Οκτώβριος 4, 2026"     ← αλλαγή μήνα
```

### Απάντηση: ΟΧΙ, δεν διαβάζεται αξιόπιστα στο frontend

Τέσσερις ανεξάρτητοι λόγοι, ο καθένας αρκετός:

| # | Πρόβλημα | Γιατί δεν λύνεται στο JS |
|---|---|---|
| 1 | **Δύο μορφές ήδη**, και δεν ξέρουμε πόσες άλλες | Η μορφή δεν είναι σύμβασή μας — είναι η σελίδα τρίτου. Αλλάζει χωρίς προειδοποίηση. |
| 2 | **Αλλαγή έτους** (`"Δεκέμβριος 28-Ιανουάριος 3, 2027"`) | Το `2027` στο τέλος δεν λέει σε ποιο από τα δύο άκρα ανήκει. Άλυτο *από την ετικέτα μόνη της*. |
| 3 | **Ελληνικά ονόματα μηνών** — ονομαστική/γενική, κεφαλαία, συντομογραφίες, μη-διασπώμενα κενά, `-` vs `–` | Θα χρειαζόταν πίνακας μηνών **αντιγραμμένος σε 4 HTML αρχεία**. Κάθε αντίγραφο μια μελλοντική απόκλιση. |
| 4 | **Το `--lang=el-GR` είναι επιλογή του scraper** (`poc/fetch_fuel_surcharge.py:55`) | Αν η DHL γυρίσει σε αγγλικά, ο parser του frontend σπάει σιωπηλά και όλα γίνονται «άκυρα» ταυτόχρονα. |

### Τι μπαίνει στη θέση του: δομημένα πεδία από το `fetch_fuel_surcharge.py`

Η ανάλυση γίνεται **μία φορά, στην Python**, όπου υπάρχει `datetime`, υπάρχει το
πλαίσιο της ημέρας σάρωσης, και το αποτέλεσμα **επαληθεύεται πριν γραφτεί**.

Νέα πεδία ανά γραμμή, στο `data/fuel_surcharge_cache.json`:

```
{ "week":       "Σεπτέμβριος 28-Οκτώβριος 4, 2026",   ← ΑΜΕΤΑΒΛΗΤΟ, τυπώνεται στο PDF
  "week_start": "2026-09-28",                          ← ΝΕΟ, ISO, Δευτέρα
  "week_end":   "2026-10-04",                          ← ΝΕΟ, ISO, Κυριακή
  "pct": 46.25, "is_next": false, "is_current": true }
```

Και ένα νέο πεδίο στην κορυφή:

```
"parse_warnings": []    ← ΝΕΟ. Μη κενό = η ανάλυση ετικέτας κάπου δεν στάθηκε.
```

**Το `week` δεν το αγγίζουμε.** Τυπώνεται αυτούσιο στο PDF
(`frontend/pricelist-clients.html:2531,2586,3004`, `api/generate_pdf.py:531-534`)
και η απόφαση 5 απαγορεύει αλλαγές εκεί.

### Πώς βγαίνουν οι ημερομηνίες στην Python

- Μήνας + ημέρα από την ετικέτα· **το έτος δεν διαβάζεται από την ετικέτα** —
  επιλέγεται εκείνο από τα `Y-1 / Y / Y+1` που τοποθετεί την εβδομάδα πιο κοντά
  στην ημέρα σάρωσης. Η αλλαγή έτους λύνεται έτσι χωρίς ειδική περίπτωση.
- **Αυτοέλεγχοι πριν την εγγραφή** (αυτό είναι το κέρδος του να γίνεται στην
  Python): κάθε εβδομάδα 7 ημερών, Δευτέρα→Κυριακή, οι γραμμές διαδοχικές και
  φθίνουσες, **ακριβώς μία** περιέχει την ημέρα σάρωσης.
- Αν κάποιος έλεγχος πέσει: `week_start`/`week_end` = `null` για τη γραμμή,
  μήνυμα στο `parse_warnings`, **και το αρχείο γράφεται κανονικά**. Ο scraper δεν
  μπλοκάρει τίποτα — μεταφέρει την αβεβαιότητα παρακάτω (απόφαση 2).

### Παλιά αντίγραφα χωρίς τα νέα πεδία

Στους browsers των χρηστών υπάρχουν ήδη αντίγραφα στο `localStorage` χωρίς
`week_start`. **Κανόνας: `week_start` απόν ⇒ ΑΓΝΩΣΤΗ εβδομάδα ⇒ κατάσταση
STALE ⇒ προειδοποίηση.** Όχι σιωπηλό πέρασμα. Αυτό είναι και ο μηχανισμός που
ξεπλένει μόνος του τα παμπάλαια cache: την πρώτη φορά που θα φανούν, θα
προκαλέσουν ανανέωση από το δίκτυο (§4).

### Η λύση: `frontend/fuel-freshness.js`

Υπάρχει ήδη το πρότυπο στο repo — `frontend/announce.js`,
`frontend/tasks-badge.js`, `frontend/shelf-grouping.js`: σκέτο αρχείο,
IIFE, φρουρός διπλής φόρτωσης, `?v=ΗΜΕΡΟΜΗΝΙΑ` στο `src`, σιωπηλή αποτυχία,
μία γραμμή ενσωμάτωσης ανά σελίδα. Χωρίς bundler, όπως όλα εδώ.

Η επιφάνεια που εκθέτει (`window.FuelFreshness`), τρία πράγματα και τίποτα άλλο:

| Κλήση | Τι κάνει | Τι επιστρέφει |
|---|---|---|
| `load()` | cache → έλεγχος → δίκτυο αν χρειαστεί (§4) | `{ air, road, week, fetched_at, state, reason }` |
| `check(data, now)` | **καθαρή συνάρτηση**, καμία παρενέργεια — διαλέγει τη γραμμή που περιέχει το `now` | `state` + η γραμμή |
| `banner(state, el)` | ζωγραφίζει την προειδοποίηση **στην οθόνη** | — |

Δύο σκληροί κανόνες για το module:

- **Δεν αλλάζει ποτέ την τιμή που χρησιμοποιεί ο καλών.** Επιστρέφει ό,τι
  επιστρέφει και σήμερα ο κώδικας, **συν** την κατάσταση. Αν το `banner()` δεν
  κληθεί ποτέ, η συμπεριφορά της σελίδας είναι bit-προς-bit η σημερινή. Αυτό
  κάνει την ενσωμάτωση αναστρέψιμη ανά σελίδα.
- **Δεν αγγίζει `document` πέρα από το στοιχείο που του δίνεται.**

### Οι τρεις καταστάσεις

| Κατάσταση | Πότε | Τιμή | Οθόνη |
|---|---|---|---|
| `OK` | υπάρχει γραμμή με `week_start ≤ σήμερα ≤ week_end` | κανονική | τίποτα |
| `STALE` | δεδομένα υπάρχουν, **καμία** γραμμή δεν περιέχει το σήμερα· ή `week_start` απόν | **η καλύτερη διαθέσιμη, χρησιμοποιείται κανονικά** | έντονη προειδοποίηση |
| `FALLBACK` | καθόλου δεδομένα, ή σκόπιμη προκαθορισμένη τιμή σελίδας | `'—'` ή η προκαθορισμένη, **σημαδεμένη** | έντονη προειδοποίηση |

Κείμενα (οθόνη μόνο):

- `STALE` — «⚠ Ο επίναυλος που εμφανίζεται είναι της εβδομάδας
  «*<ετικέτα>*» και έχει **περάσει**. Ελέγξτε το ⛽ Επίναυλος πριν στείλετε.»
- `STALE` χωρίς `week_start` — «⚠ Δεν μπορεί να επιβεβαιωθεί η εβδομάδα του
  επίναυλου. Ελέγξτε το ⛽ Επίναυλος.»
- `FALLBACK` με προκαθορισμένες — «⚠ Δεν φορτώθηκαν δεδομένα επίναυλου.
  Εμφανίζονται **προκαθορισμένες** τιμές (AIR 47.0% / ROAD 35.25%) που **δεν
  είναι οι τρέχουσες**.» (απόφαση 4)
- `FALLBACK` χωρίς τίποτα — «⚠ Δεν φορτώθηκαν δεδομένα επίναυλου. Τα ποσοστά
  εμφανίζονται ως «—».»

### 3.1 Τα `parse_warnings` φαίνονται στο dashboard

Το `parse_warnings` (§2) γεμίζει όταν η ανάλυση της ετικέτας δεν στάθηκε: άγνωστος
μήνας, εβδομάδα που δεν είναι Δευτέρα→Κυριακή, κενό στη σειρά των εβδομάδων,
καμία εβδομάδα που να περιέχει τη σημερινή ημερομηνία. Αν κάθεται μόνο μέσα στο

## 4. (γ) Το cache: λήγει ή σημαδεύεται;

### Απάντηση: **σημαδεύεται. Δεν διαγράφεται ποτέ.**

Δύο λόγοι:

1. Η διαγραφή σε συνθήκες χωρίς δίκτυο αφήνει **τίποτα** στην οθόνη. Τότε οι
   μόνες επιλογές είναι μπλοκάρισμα (απαγορεύεται, απόφαση 2) ή παύλες. Ένα
   παλιό νούμερο **με κόκκινη προειδοποίηση** είναι χρησιμότερο στον πωλητή από
   μια παύλα: ξέρει την τάξη μεγέθους και ξέρει ότι πρέπει να ελέγξει.
2. Είναι μη αναστρέψιμη ενέργεια σε δεδομένα που δεν έχουμε από αλλού.

### Αλλά αντιστρέφεται η προτεραιότητα

**Αυτό είναι το πραγματικό σφάλμα σήμερα**, όχι η απουσία TTL. Το σημερινό
μοτίβο (`:2210`, `:2711`, `:3075`) χτυπά το δίκτυο **μόνο σε αστοχία cache**:

```
αν cache άδειο → φέρε από δίκτυο
```

Γι' αυτό ένα cache δεν ανανεώνεται ποτέ. Καμία γραμμή `removeItem('4a_fuel_cache')`
δεν υπάρχει πουθενά στο repo. Το νέο μοτίβο:

| Βήμα | Συνθήκη | Ενέργεια |
|---|---|---|
| 1 | — | διάβασε cache, τρέξε `check()` |
| 2 | `OK` | **χρησιμοποίησέ το, χωρίς δίκτυο** — η εβδομάδα είναι σωστή, δεν υπάρχει τίποτα να κερδίσουμε |
| 3 | όχι `OK` | ζήτα από δίκτυο |
| 4 | το δίκτυο απάντησε | γράψε cache, ξανα-`check()` |
| 5 | το δίκτυο έπεσε, **υπάρχει** παλιό cache | κράτα την παλιά τιμή, `STALE`, αιτία «δίκτυο» |
| 6 | το δίκτυο έπεσε, **δεν** υπάρχει cache | `FALLBACK` |

Το βήμα 2 είναι που κάνει τη δουλειά εκτός δικτύου να παραμένει γρήγορη, και το
βήμα 3 είναι που θεραπεύει το παγωμένο cache.

### Τι βλέπει ο χρήστης με το δίκτυο κάτω

| | cache σωστής εβδομάδας | cache περασμένης | κανένα cache |
|---|---|---|---|
| `pricelist-clients` | κανονική λειτουργία, **καμία** προειδοποίηση | παλιό %, κόκκινη λωρίδα, **η προσφορά βγαίνει** | `'—'`, κόκκινη λωρίδα, η προσφορά βγαίνει |
| `pricelist-editor` | κανονικά | παλιό %, κόκκινο `fc-info` | σήμερα `getFcPct()`→**0**· **γίνεται `FALLBACK`+προειδοποίηση** |
| `pricelist-table` | κανονικά | παλιό %, κόκκινο badge | 47.0/35.25 **σημαδεμένα** (απόφαση 4) |
| dashboard | κανονικά | λωρίδα | υπάρχον κόκκινο κουτί |

### Το υπάρχον φράγμα αρχειοθέτησης μένει ως έχει

Στο `pricelist-clients.html:3218-3223` υπάρχει σήμερα έλεγχος που **μπλοκάρει**
την αρχειοθέτηση αν λείπει η τιμή (`missing.push('fuel.air')`). Δεν το πειράζουμε.
Δεν έρχεται σε σύγκρουση με την απόφαση 2, γιατί αφορά **απουσία** τιμής, όχι
**παλαιότητα**: ένα snapshot χωρίς επίναυλο δεν αναπαράγεται ποτέ. Μια `STALE`
τιμή περνάει το φράγμα ακριβώς όπως και σήμερα — απλώς τώρα ο χρήστης το βλέπει.

## 5. (δ) `is_current = (i == 1)` — από ημερομηνία;

### Απάντηση: ναι, και είναι **μικρή** αλλαγή — αλλά όχι εκεί που φαίνεται

Σήμερα (`poc/fetch_fuel_surcharge.py:153-156`):

```python
row['is_next']    = (i == 0)
row['is_current'] = (i == 1)
```

Καθαρή θέση στον πίνακα. Υπόθεση: η DHL λιστάρει **πάντα** πρώτη την επόμενη
εβδομάδα. Καμία διασταύρωση με `datetime.now()` πουθενά.

Μόλις υπάρχουν `week_start`/`week_end` (§2), ο κανόνας γίνεται ημερολογιακός
μέσα στην **ίδια συνάρτηση** `enrich_data()`: τρέχουσα = αυτή που περιέχει την
ημέρα σάρωσης, επόμενη = η αμέσως μετά. Τα `current_air`/`current_road`
(`:146-147`, σήμερα `air[1]['pct']`) προκύπτουν από τη σημαδεμένη γραμμή.

**Μέγεθος: μία συνάρτηση, ~10 γραμμές.** Το κόστος δεν είναι στις γραμμές —
είναι στα δύο παρακάτω.

### Πρώτο: τα δύο πεδία είναι ήδη το 90% της δουλειάς

Χωρίς `week_start` η ημερολογιακή παραγωγή δεν γίνεται καθόλου. Με αυτά,
γίνεται σχεδόν δωρεάν. Άρα **δεν είναι χωριστό έργο** — είναι η φυσική συνέχεια
του §2 και μπαίνει στο ίδιο PR του scraper.

### Δεύτερο: ποιος είναι ο αυθεντικός κριτής

Μετά την αλλαγή υπάρχουν **δύο** αξιολογήσεις του ίδιου κατηγορήματος: του
scraper (ώρα σάρωσης) και του frontend (ώρα χρήσης). Δεν συμπίπτουν πάντα — το
αρχείο γράφεται 05:00 UTC και διαβάζεται όποτε να 'ναι, ενδεχομένως μέρες μετά.

Κανόνας: **αυθεντικό είναι το frontend.** Το `check()` διαλέγει γραμμή με
`week_start ≤ σήμερα ≤ week_end` και **δεν εμπιστεύεται το `is_current`**. Πέφτει
πίσω στο `is_current` μόνο όταν λείπουν οι ημερομηνίες (παλιό cache) — και τότε
η κατάσταση είναι ούτως ή άλλως `STALE`.

Το `is_current` παραμένει στο αρχείο: το διαβάζει το `api/generate_pdf.py:103-107`
και το dashboard (`:141-143,161-181`), και κάνει το JSON αναγνώσιμο από άνθρωπο.
Απλώς παύει να είναι η μοναδική αλήθεια.

### Πότε ακριβώς διαφέρουν οι δύο κανόνες — ΕΠΙΒΕΒΑΙΩΜΕΝΟ ΣΦΑΛΜΑ

Η υπόθεση ήταν «σε κανονική μέρα, ποτέ». **Είναι λάθος.** Έλεγχος των 40
τελευταίων εκδόσεων του `data/fuel_surcharge_cache.json` (git ιστορικό,
17/08→26/09/2026), με το κριτήριο «περιέχει η σημαδεμένη εβδομάδα την ημέρα
σάρωσης;»:

| Ημέρα σάρωσης | Εκδόσεις | Η θέση `i==1` έδειξε |
|---|---|---|
| Δευτέρα–Παρασκευή | 29 | **σωστή** εβδομάδα, 29/29 |
| Σάββατο & Κυριακή | 11 | **λάθος** εβδομάδα, 11/11 — την **επόμενη** |

Χωρίς εξαίρεση, προς καμία κατεύθυνση. Η εξήγηση είναι στα ίδια τα δεδομένα:
**η DHL προσθέτει τη γραμμή της νέας εβδομάδας στην κορυφή του πίνακα το
Σάββατο.** Από εκείνη τη στιγμή ο πίνακας έχει μία επιπλέον μελλοντική γραμμή,
οπότε η θέση `i==1` παύει να είναι η τρέχουσα εβδομάδα και γίνεται η επόμενη.

Συνέπεια, ενεργή σήμερα: **κάθε προσφορά που φτιάχτηκε Σάββατο ή Κυριακή
τυπώνει τον επίναυλο της επόμενης εβδομάδας** — ποσοστό *και* ετικέτα. Το
αρχείο της 26/09/2026 (Σάββατο) γράφει `current_air: 46.25` ενώ η εβδομάδα σε
εξέλιξη (Σεπ 21-27) είναι **45.0**. Διαφορά 1.25 μονάδες, στις 2 από τις 7
ημέρες.

### Πιθανή εξήγηση του περιστατικού 19-20/09

Εκείνο το Σαββατοκύριακο (Σάββατο 19 και Κυριακή 20/09) το αρχείο έδειχνε:

| | Τι έγραφε το αρχείο | Η εβδομάδα σε εξέλιξη (Σεπ 14-20) |
|---|---|---|
| AIR | 45.0% (εβδομάδα Σεπ 21-27) | **43.75%** |
| ROAD | 37.0% (εβδομάδα Σεπ 21-27) | **35.5%** |

Υπερχρέωση 1.25 μονάδες AIR, 1.5 ROAD, και στα δύο 24ωρα.

Το κρίσιμο: **τη Δευτέρα 21/09 τα ίδια ακριβώς νούμερα (45.0 / 37.0) έγιναν
σωστά.** Αν κάποιος ανέφερε λάθος επίναυλο εκείνο το διήμερο και ο έλεγχος έγινε
τη Δευτέρα, δεν υπήρχε πια τίποτα να βρεθεί — η ένδειξη είχε αυτοδιορθωθεί, το
αρχείο έδειχνε το ίδιο ποσοστό, και κάθε προσπάθεια αναπαραγωγής θα έβγαζε
«δουλεύει κανονικά».

*Υπόθεση.* Δεν υπάρχει καταγραφή του περιστατικού στο repo· η χρονική σύμπτωση
και το μέγεθος της απόκλισης ταιριάζουν, τίποτα παραπάνω.

### Η διόρθωση

Ο ημερολογιακός κανόνας διορθώνει και τις 11 περιπτώσεις χωρίς ειδική ρύθμιση:
δεν ξέρει τίποτα για Σάββατα, απλώς δεν κοιτά τη θέση.

Οι υπόλοιπες αποκλίσεις που προβλέπονταν (η DHL αναδιατάσσει τον πίνακα, δεν
δημοσιεύει «επόμενη», ή το Action πέφτει για μέρες) παραμένουν ισχυρές — απλώς
δεν χρειάστηκε να τις περιμένουμε για να δούμε το πρόβλημα.

Σημείωση χωρίς ενέργεια: το `poc/fetch_fuel_surcharge.py` είναι παραγωγή — το
τρέχει το `.github/workflows/update_fuel_surcharge.yml:32` — παρότι κάθεται στο
`poc/`. Δεν μετακινείται σε αυτή τη φάση.

## 6. Το snapshot (απόφαση 3)

Σήμερα (`frontend/pricelist-clients.html:3294-3295`):

```
fuel: { air_pct, road_pct, week, source:'fuel_surcharge_cache.json' }
```

Προστίθενται **δύο** πεδία:

```
fuel: { air_pct, road_pct, week,
        fetched_at,        ← ΝΕΟ (απόφαση 3)
        week_start,        ← ΝΕΟ, ώστε η παλαιότητα να αποδεικνύεται, όχι να εικάζεται
        freshness,         ← ΝΕΟ: 'ok' | 'stale' | 'fallback' — τι ίσχυε τη στιγμή της αποστολής
        source }
```

Το `freshness` είναι το ουσιώδες: χωρίς αυτό, τρεις μήνες μετά δεν ξεχωρίζεις
την προσφορά που στάλθηκε με σωστό επίναυλο από εκείνη που στάλθηκε με
προειδοποίηση αγνοημένη.

**Καμία μετανάστευση βάσης.** Το `4a_offers.snapshot` είναι JSON NOT NULL και
χωρίς σχήμα (`docs/snapshot_spec.md`). Η στήλη `fuel_pct`
(`api/offer_archive.php:169,251`) δεν αγγίζεται.

## 10. Ανοιχτά σημεία

1. **Ακριβής μορφή αλλαγής έτους.** Ο κανόνας δοκιμάστηκε σε **κατασκευασμένο**
   δείγμα (`Δεκέμβριος 28-Ιανουάριος 3, 2027` με σημείο αναφοράς 30/12/2026 →
   σωστό) — όχι σε πραγματικό. Η μορφή είναι εικασία, βασισμένη στη μορφή
   αλλαγής μήνα που **έχουμε**. Το `parse_warnings` καλύπτει την αστοχία χωρίς
   ζημιά, αλλά το σημείο κλείνει μόνο με πραγματικό δείγμα Δεκεμβρίου.
2. **Ώρα του πελάτη.** Ο έλεγχος τρέχει στο ρολόι του browser. Ένας υπολογιστής
   με λάθος ημερομηνία θα δει ψευδές `STALE` — θόρυβος, όχι ζημιά (καμία
   παρεμπόδιση, τίποτα στο PDF). Δεν προτείνεται αντιμετώπιση.
3. **Δευτέρα πρωί, πριν τις 05:00 UTC.** Το Action δεν έχει τρέξει ακόμα για τη
   νέα εβδομάδα. Αν η DHL έχει ήδη δημοσιεύσει τη νέα εβδομάδα την Παρασκευή
   (το `is_next` υπάρχει, άρα συνήθως ναι), το αρχείο την περιέχει και ο έλεγχος
   τη βρίσκει κανονικά. Αν όχι, η Δευτέρα ξεκινά με `STALE` για λίγες ώρες —
   **σωστά**, γιατί όντως δεν ξέρουμε το νούμερο της εβδομάδας.
