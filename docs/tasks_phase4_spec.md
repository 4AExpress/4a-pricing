## Οι κλειδωμένες αποφάσεις

1. **Random ανάθεση στο ΞΕΚΛΕΙΔΩΜΑ**, όχι στη δημιουργία.
2. **Απόρριψη με κωδικοποιημένο λόγο** από πίνακα στη βάση, και η
   εργασία ξαναπάει random σε **ΑΛΛΟΝ** δικαιούχο — ποτέ στον ίδιο.
3. **Steal ελεύθερο** για όποιον έχει τη δεξιότητα, πάντα
   καταγεγραμμένο, ορατό ποιος τράβηξε από ποιον.
4. **Χωρίς υποψήφιο** → ουρά με σήμανση «απορρίφθηκε» + κόκκινο σήμα.

## 1. Πού μπαίνει η random ανάθεση

### Συμφωνώ με την πρόταση, με μία διόρθωση στη διατύπωση

Η πρότασή σου — «στο `done`/`na`, να βρίσκει τις εξαρτημένες και να τις
αναθέτει» — είναι σωστή. Η διόρθωση αφορά το **γιατί**:

**Το ξεκλείδωμα δεν είναι γεγονός· είναι παράγωγο.** Το `locked`
υπολογίζεται κάθε φορά που διαβάζεται λίστα, στο
`api/tasks_lib.php:35-41`:

```sql
CASE WHEN tt.`depends_on` IS NULL THEN 0
     WHEN EXISTS (SELECT 1 FROM `4a_tasks` d
                   WHERE d.`client_id` = t.`client_id`
                     AND d.`offer_number` = t.`offer_number`
                     AND d.`task_code` = tt.`depends_on`
                     AND d.`status` IN ('done','na'))
     THEN 0 ELSE 1 END AS `locked`
```

Καμία στήλη δεν αλλάζει όταν κάτι ξεκλειδώνει. Άρα **δεν υπάρχει στιγμή
που «συμβαίνει» το ξεκλείδωμα** — υπάρχει μόνο η στιγμή που αλλάζει η
**αιτία** του: όταν η προηγούμενη εργασία κλείνει.

Αυτό σημαίνει ότι η ανάθεση πρέπει να μπει στο **μοναδικό σημείο που
μπορεί να αλλάξει το `locked` κάποιας άλλης εργασίας**: το κλείσιμο.

### Τα ακριβή σημεία

| Αρχείο:γραμμή | Τι είναι |
|---|---|
| `api/tasks_lib.php:257-268` | `tasks_done()` — `UPDATE ... status='done'` στο `:262`, event στο `:265` |
| `api/tasks_lib.php:270-287` | `tasks_na()` — `UPDATE ... status='na'` στο `:282`, event στο `:285` |

Η κλήση μπαίνει **μετά το event και πριν το `return`** και στα δύο:

```
tasks_unlock_and_assign($db, $task['client_id'], $task['offer_number'],
                        $task['task_code'], $actorId)
```

Δηλαδή: «μόλις έκλεισε η `X` για αυτόν τον πελάτη και αυτή την προσφορά —
βρες ό,τι είχε `depends_on = X`, δες τι ξεκλείδωσε όντως, και ανάθεσέ το».

### Ψευδοκώδικας

```
function tasks_unlock_and_assign(db, clientId, offerNo, closedCode, actorId):

    # Ποιες εργασίες ΤΟΥ ΙΔΙΟΥ πελάτη/προσφοράς εξαρτιόνταν από αυτήν
    # ΚΑΙ είναι ακόμα ανοιχτές και αδιάθετες.
    candidates = SELECT t.* FROM 4a_tasks t
                   JOIN 4a_task_types tt ON tt.code = t.task_code
                  WHERE t.client_id = :clientId
                    AND t.offer_number = :offerNo
                    AND tt.depends_on = :closedCode
                    AND t.status = 'open'
                    AND t.assigned_to IS NULL

    for task in candidates:
        # ΞΑΝΑΕΛΕΓΞΕ το locked με τον ΙΔΙΟ υπολογισμό — μην υποθέσεις ότι
        # ξεκλείδωσε. Με αλυσίδα βάθους >1 μπορεί να περιμένει και άλλη.
        if task.locked == 1: continue
        tasks_auto_assign(db, task, actorId, 'ξεκλείδωσε μετά το ' + closedCode)
```

Και η ίδια η επιλογή:

```
function tasks_auto_assign(db, task, actorId, why):

    # Δικαιούχοι: δεξιότητα για ΑΥΤΟΝ τον κωδικό, σε ΑΥΤΗ τη χώρα,
    # ΕΝΕΡΓΟΙ, και ΠΟΤΕ όσοι την έχουν ήδη απορρίψει.
    pool = SELECT s.user_id FROM 4a_user_task_skills s
             JOIN 4a_users u ON u.id = s.user_id
            WHERE s.task_code = task.task_code
              AND s.country IN (clientCountry, 'BOTH')
              AND u.active = 1
              AND u.role <> 'administrator'        # οι admins δεν είναι υποψήφιοι
              AND s.user_id NOT IN (SELECT user_id FROM 4a_task_rejections
                                     WHERE task_id = task.id)

    if pool is empty:
        # Τίποτα δεν αλλάζει στην ανάθεση· μπαίνει ΣΗΜΑΝΣΗ.
        UPDATE 4a_tasks SET needs_attention = 1 WHERE id = task.id
        event(task.id, 'no_candidate', NULL, 'κανένας δικαιούχος — μένει στην ουρά')
        return

    winner = pool[ random ]
    # Ίδιο μοτίβο με το claim (tasks_lib.php:212-216): ο όρος μέσα στο
    # UPDATE, ώστε δύο ταυτόχρονες αναθέσεις να μη συγκρούονται.
    UPDATE 4a_tasks SET assigned_to = :winner, status = 'in_progress'
     WHERE id = :taskId AND assigned_to IS NULL AND status = 'open'
    if rowCount == 0: return        # κάποιος πρόλαβε, δεν πειράζει

    event(task.id, 'auto_assigned', actorId, why + ' — τυχαία ανάθεση')
```

**Ο τυχαίος διαλέγεται στην PHP, όχι με `ORDER BY RAND()`.** Το `RAND()`
σε join με δύο πίνακες είναι αδιαφανές και δεν λογοδοτεί· μια `shuffle()`
πάνω σε λίστα 3-5 ονομάτων είναι το ίδιο τυχαία και ελέγξιμη σε test.

### Τρία που πρέπει να προσεχθούν

**Η ίδια συναλλαγή.** Το `tasks_done` δεν ανοίγει σήμερα συναλλαγή. Η
ανάθεση πρέπει να είναι **στην ίδια** με το κλείσιμο, αλλιώς μια αποτυχία
αφήνει εργασία κλειστή και την επόμενη μόνιμα αδιάθετη.

**Το `tasks_assign` με `force`** (`api/tasks_lib.php:297`) μπορεί να
κλείσει εργασία που ήταν κλειδωμένη. Τότε η εξαρτημένη ξεκλειδώνει από
`done` που δεν έπρεπε να συμβεί. Δεν το εμποδίζουμε — αλλά το
`tasks_unlock_and_assign` πρέπει να τρέχει **και** σε αυτή την περίπτωση,
αφού η αλυσίδα όντως προχώρησε.

**Αλυσίδα βάθους > 1.** Όταν κλείσει το `open_code`, ξεκλειδώνουν
`cms_rates`, `notify_client`, `cod_form`, `training` — τέσσερις μαζί.
Τέσσερις τυχαίες αναθέσεις στην ίδια στιγμή. Αυτό είναι το ζητούμενο,
αλλά αξίζει να το ξέρει κανείς πριν το δει.

## 2. Οι ρίζες — πότε τους γίνεται ανάθεση

**Σωστή παρατήρηση: το `open_code` δεν ξεκλειδώνει ποτέ**, γιατί
γεννιέται ξεκλείδωτο (`depends_on IS NULL` → `locked = 0` στο
`tasks_lib.php:35`). Αν η ανάθεση γίνεται μόνο «στο ξεκλείδωμα», η μόνη
ρίζα δεν θα ανατίθεται ποτέ — και επειδή είναι η **μοναδική** ρίζα,
τίποτα δεν θα ξεκινούσε αυτόματα.

### Η αρχή, ξαναδιατυπωμένη

> Η τυχαία ανάθεση γίνεται τη στιγμή που μια εργασία **γίνεται
> διαθέσιμη**. Για τις εξαρτημένες, αυτή η στιγμή είναι το κλείσιμο της
> προηγούμενης. Για τις ρίζες, είναι η **δημιουργία**.

Δεν είναι εξαίρεση στον κανόνα — είναι ο ίδιος κανόνας. Το «όχι στη
δημιουργία» σημαίνει «όχι σε **όλες** στη δημιουργία», που ήταν και το
πρόβλημα: αλλιώς οι έξι κλειδωμένες θα ανατίθονταν σε κόσμο που δεν
μπορεί να τις ξεκινήσει.

### Το σημείο

`api/tasks_create.php:134-158`, μέσα στον βρόχο, **μετά** το event
`created` στο `:157`:

```
if (t.depends_on IS NULL)
    tasks_auto_assign(db, newTask, actorId, 'ρίζα αλυσίδας')
```

Ίδια συνάρτηση, ίδιος κανόνας εξαίρεσης, ίδιο event `auto_assigned`.

**Το `tasks_create.php` έχει ήδη συναλλαγή** (`:126`) — η ανάθεση μπαίνει
μέσα της δωρεάν.

**Και η εγγύηση της Φάσης 2 μένει:** αν η ανάθεση σκάσει, το
`try/catch` του `tasks_create_for_client` την πιάνει και η αποθήκευση
πελάτη δεν χαλάει. Πρέπει όμως η ανάθεση να **μην** ρίχνει τη δημιουργία:
καλύτερα εργασίες αδιάθετες παρά καθόλου εργασίες.

## 3. Σχήμα

### 3α. `4a_task_reject_reasons` — νέος

Οι λόγοι σε πίνακα, όχι σταθερές στον κώδικα, με το ίδιο σκεπτικό που
οδήγησε στο `4a_task_statuses`: νέος λόγος = γραμμή στη βάση.

```sql
CREATE TABLE `4a_task_reject_reasons` (
  `code`          VARCHAR(40)  NOT NULL,
  `label`         VARCHAR(120) NOT NULL,
  `task_code`     VARCHAR(40)      NULL COMMENT 'NULL = ισχύει για κάθε τύπο',
  `requires_note` TINYINT(1)   NOT NULL DEFAULT 0,
  `sort_order`    INT          NOT NULL DEFAULT 0,
  `active`        TINYINT(1)   NOT NULL DEFAULT 1,
  `created_at`    TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`code`),
  KEY `ix_task_active` (`task_code`, `active`, `sort_order`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

Το `task_code` επιτρέπει λόγους ειδικούς ανά τύπο χωρίς δεύτερο πίνακα.
`NULL` = καθολικός.

### Οι αρχικοί λόγοι (απόφαση 24/09)

| `code` | `label` | `sort_order` | `requires_note` |
|---|---|---|---|
| `workload` | Φόρτος εργασίας | 10 | 0 |
| `absent` | Απουσία / άδεια | 20 | 0 |
| `no_knowledge` | Δεν γνωρίζω τη διαδικασία | 30 | 0 |
| `wrong_person` | Δεν είναι δική μου αρμοδιότητα | 40 | 0 |
| `other` | Άλλο | 50 | **1** |

**Όλοι καθολικοί** — `task_code = NULL` σε όλους. Κανένας δεν δένεται με
συγκεκριμένο τύπο εργασίας.

**Το `requires_note` είναι στήλη, όχι `if ($code === 'other')` στην PHP.**
Ο κανόνας «το Άλλο θέλει εξήγηση» ανήκει στον ίδιο πίνακα με τον λόγο·
αλλιώς ένας νέος λόγος που χρειάζεται σχόλιο θα απαιτούσε deploy. Ο
έλεγχος στο `reject` διαβάζει τη στήλη:

```
if (reason.requires_note && trim(note) === '')
    return 400 'ο λόγος αυτός απαιτεί σχόλιο'
```

Το `no_knowledge` αξίζει προσοχή στη χρήση: δηλώνει ότι κάποιος έχει τη
δεξιότητα στο `4a_user_task_skills` αλλά δεν θα έπρεπε. Δεν το διορθώνει
αυτόματα ο κώδικας — αλλά μετριέται, και αυτός είναι ο λόγος που οι λόγοι
είναι κωδικοποιημένοι.

### 3β. `4a_task_rejections` — νέος

Ο πυρήνας του «ποτέ στον ίδιο».

```sql
CREATE TABLE `4a_task_rejections` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `task_id`     BIGINT UNSIGNED NOT NULL,
  `user_id`     INT             NOT NULL,
  `reason_code` VARCHAR(40)     NOT NULL,
  `note`        VARCHAR(200)        NULL COMMENT 'προαιρετικό, πέρα από τον κωδικό',
  `created_at`  TIMESTAMP       NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uq_task_user` (`task_id`, `user_id`),
  KEY `ix_task` (`task_id`),
  KEY `ix_reason` (`reason_code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**Το `UNIQUE(task_id, user_id)` είναι ο κανόνας**, όχι σχόλιο: ο ίδιος
δεν μπορεί να απορρίψει δύο φορές την ίδια εργασία, και το `NOT IN` του
pool διαβάζει ακριβώς αυτόν τον πίνακα. Ένα `varchar` μέσα στα events δεν
θα ήταν αξιόπιστο φίλτρο.

**Χωριστός πίνακας και όχι στήλη στο `4a_tasks`**, γιατί οι απορρίψεις
είναι πολλές ανά εργασία.

### 3γ. `4a_tasks` — μία στήλη

```sql
ALTER TABLE `4a_tasks`
  ADD COLUMN `needs_attention` TINYINT(1) NOT NULL DEFAULT 0
    COMMENT 'απορρίφθηκε και δεν έμεινε υποψήφιος' AFTER `status`;
ALTER TABLE `4a_tasks` ADD KEY `ix_attention` (`needs_attention`, `status`);
```

Γιατί στήλη και όχι υπολογισμός: το κόκκινο σήμα το χρειάζεται σε κάθε
φόρτωση σελίδας. Ένα `COUNT` με τριπλό `NOT EXISTS` πάνω σε δεξιότητες
και απορρίψεις, σε κάθε άνοιγμα, δεν αξίζει. Η στήλη γίνεται `0` μόλις
κάποιος την αναλάβει.

### 3δ. `4a_task_events` — μία στήλη

```sql
ALTER TABLE `4a_task_events`
  ADD COLUMN `meta` JSON NULL COMMENT 'δομημένα: from_user, to_user, reason_code'
  AFTER `note`;
```

Το `note` μένει ανθρώπινο κείμενο. Το `meta` κρατά τα δομημένα, ώστε το
«ποιος τράβηξε από ποιον» να **διαβάζεται**, όχι να διαβάζεται-με-regex.

### 3ε. Νέα events

| `event` | `actor_id` | `meta` | Πότε |
|---|---|---|---|
| `auto_assigned` | ποιος πυροδότησε (ή NULL) | `{to_user, why}` | τυχαία ανάθεση |
| `rejected` | ο απορρίπτων | `{reason_code}` | απόρριψη |
| `no_candidate` | NULL | `{}` | δεν έμεινε κανείς |
| `stolen` | ο **νέος** κάτοχος | `{from_user, to_user}` | steal |

Το `4a_task_events.event` είναι `varchar(30)` ακριβώς για αυτό — καμία
`ALTER` σε ENUM δεν χρειάζεται.

### 3στ. Ενέργειες API

| Ενέργεια | Σώμα | Έλεγχοι |
|---|---|---|
| `reject` | `{id, reason_code, note?}` | ο **ανάδοχος** μόνο· ο `reason_code` υπάρχει και είναι `active`· **αν `requires_note`, το `note` είναι υποχρεωτικό**· η εργασία σε `in_progress` |
| `steal` | `{id}` | ο αιτών **έχει τη δεξιότητα** για τον κωδικό και τη χώρα· η εργασία **ανατεθειμένη σε άλλον**· δεν είναι κλειδωμένη |
| `reject_reasons` | `GET ?action=reject_reasons&task_code=` | λίστα για το UI, με το `requires_note` |
| `history` | `GET ?action=history&id=` | τα events μιας εργασίας, με ώρα και **όνομα** — βλ. §4β |

**Ο `reject` δεν κλείνει την εργασία.** Καθαρίζει το `assigned_to`,
γράφει στο `4a_task_rejections`, και καλεί ξανά `tasks_auto_assign`. Η
εργασία επιστρέφει σε `open`.

**Ο `steal` δεν ζητά άδεια** — αυτό αποφασίστηκε. Αλλά γράφει event με
`from_user`, και ο προηγούμενος κάτοχος πρέπει να το δει στην οθόνη του.

## 4. Το κόκκινο σήμα

### Τι μετράει

```sql
SELECT COUNT(*) FROM `4a_tasks`
 WHERE `needs_attention` = 1 AND `status` = 'open'
```

Καλύπτεται από το `ix_attention`. **Ένας αριθμός, ένα ευρετήριο.**

Ποιος το βλέπει: όποιος έχει `tasks.view`. Είναι σήμα ότι **κάτι
κόλλησε**, όχι προσωπική ειδοποίηση — δεν φιλτράρεται με δεξιότητες,
αλλιώς ακριβώς οι εργασίες που δεν έχουν δικαιούχο δεν θα φαίνονταν σε
κανέναν.

Το scope χώρας **ισχύει** (`tasks_lib.php:81`): χρήστης GR δεν μετράει
κολλημένες κυπριακές.

### Πού μπαίνει, δεδομένου ότι το nav είναι αντιγραμμένο 11 φορές

**Όχι επεξεργασία 11 αρχείων.** Νέο `frontend/tasks-badge.js`, με το
μοτίβο του `shelf-grouping.js`:

```js
// βρίσκει ΤΟΝ ΣΥΝΔΕΣΜΟ, όχι τη σελίδα
document.querySelectorAll('a[href="tasks.html"]').forEach(...)
```

Το script **στοχεύει τον σύνδεσμο**. Σε σελίδα χωρίς αυτόν δεν κάνει
τίποτα — σιωπηλά, χωρίς σφάλμα. Έτσι η προσθήκη του σε νέα σελίδα είναι
μία γραμμή `<script src>`, και ο σύνδεσμος μπορεί να μπει σε άλλες 8
σελίδες ανεξάρτητα, όποτε αποφασιστεί.

Ενσωμάτωση αρχικά μόνο στις **τρεις** που έχουν ήδη τον σύνδεσμο:
`pricelist-clients.html`, `pricelist-editor.html`, `users.html`.

**Κόστος:** ένα `GET tasks.php?action=badge` ανά φόρτωση αυτών των
σελίδων. Επιστρέφει `{attention: n, mine: n}`. Το `?v=` στο `<script src>`
όπως στο `shelf-grouping.js`.

**Σιωπηλή αποτυχία υποχρεωτική:** αν το endpoint πέσει, το σήμα δεν
εμφανίζεται — δεν σπάει η σελίδα πελατών επειδή κόλλησε το σύστημα
εργασιών. Ίδια αρχή με το `announce.js` (*«ΠΟΤΕ δεν μπλοκάρει τη
σύνδεση. Κάθε σφάλμα καταπίνεται»*).

### 4β. Ιστορικό ανά εργασία — ΜΠΑΙΝΕΙ στη Φάση 4 (απόφαση 24/09)

Πτυσσόμενο κάτω από κάθε γραμμή εργασίας. Κλειστό εξ ορισμού — ανοίγει
με κλικ σε «ιστορικό».

```sql
SELECT e.`event`, e.`note`, e.`meta`, e.`created_at`,
       u.`name` AS actor_name
  FROM `4a_task_events` e
  LEFT JOIN `4a_users` u ON u.`id` = e.`actor_id`
 WHERE e.`task_id` = ?
 ORDER BY e.`id`
```

Καλύπτεται από το υπάρχον `ix_task_time` (`task_id`, `created_at`).

Το `LEFT JOIN` είναι απαραίτητο: το `actor_id` είναι `NULL` στα
`auto_assigned` και `no_candidate`, που τα κάνει το σύστημα. Εμφάνιση
«Σύστημα» όταν λείπει όνομα.

Μία γραμμή ανά συμβάν: **ώρα · όνομα · τι έγινε**. Για το `stolen`, το
`meta.from_user` δίνει το «τράβηξε από **X**» — εκεί κερδίζει το
δομημένο `meta` έναντι κειμένου.

Φόρτωση **κατ' απαίτηση**, ένα αίτημα ανά εργασία όταν ανοίγει. Να μη
φορτώνεται μαζί με τη λίστα: με 7 εργασίες × 10 πελάτες θα ήταν 70
υποερωτήματα για κάτι που συνήθως δεν κοιτάζει κανείς.

## 5. Τι ΔΕΝ μπαίνει στη Φάση 4

| Εκτός πεδίου | Γιατί |
|---|---|
| **SLA / `due_at`** | Τα `sla_hours` είναι `NULL` παντού. Χωριστό θέμα. |
| **Email ειδοποιήσεις** | Το σήμα είναι οπτικό, μέσα στην πλατφόρμα. Το email θέλει απόφαση για συχνότητα και παραλήπτες. |
| **Βάρη στην τυχαιότητα** | Ομοιόμορφη επιλογή. Εξισορρόπηση φόρτου («ο λιγότερο φορτωμένος») είναι διαφορετικό πρόβλημα και θέλει δεδομένα που δεν έχουμε ακόμα. |
| **Όριο απορρίψεων** | Κανένα «μετά από 3 απορρίψεις κάνε X». Η στοίβα με `needs_attention` είναι το σήμα. |
| **Επαναφορά απόρριψης** | Άπαξ και απέρριψες, δεν ξαναγίνεσαι υποψήφιος για **αυτή** την εργασία. Αναίρεση θέλει `DELETE` στο `4a_task_rejections`, χωρίς UI. |
| **Steal από κλειδωμένη** | Κλειδωμένη δεν ανατίθεται, άρα δεν κλέβεται. |
| **Ειδοποίηση στον κλεμμένο** | Το βλέπει όταν ανοίξει την οθόνη· καμία ώθηση. |
| **`paused` / `resume`** | Ακόμα χωρίς ενέργεια, από τη Φάση 3. |
| **`display_name`** | Η σύνοψη και το ιστορικό δείχνουν το πλήρες `name`. |
| **Ιστορικό σε επίπεδο πελάτη** | Πτυσσόμενο **ανά εργασία** (§4β). Συγκεντρωτικό ιστορικό όλης της αλυσίδας ενός πελάτη δεν μπαίνει. |

## Αποφάσεις που έκλεισαν στις 24/09

**1. Οι λόγοι απόρριψης** ορίστηκαν — πέντε, όλοι καθολικοί, με το `other`
να απαιτεί σχόλιο μέσω της στήλης `requires_note`. Βλ. §3α.

**2. Οι διαχειριστές μένουν εκτός pool.** Συνέπεια, ρητά **επιθυμητή**:
με μηδέν δεξιότητες CY, **κάθε κυπριακή εργασία πηγαίνει κατευθείαν σε
`needs_attention`** και ανάβει το κόκκινο σήμα από την πρώτη μέρα. Αυτό
είναι το ζητούμενο — η ορατή στοίβα είναι το σήμα ότι λείπει η απόφαση
για την Κύπρο, όχι σφάλμα προς διόρθωση.

**3. Το ιστορικό μπαίνει** στη Φάση 4, πτυσσόμενο ανά εργασία, με ώρα και
όνομα. Βλ. §4β.

## Ανοιχτό, πριν γραφτεί κώδικας

**Ποιος μπορεί να δει το ιστορικό;** Ο έλεγχος είναι `tasks.view` και το
scope χώρας — δηλαδή όποιος βλέπει την εργασία βλέπει και ποιος την
απέρριψε και με τι λόγο. Με το `no_knowledge` («δεν γνωρίζω τη
διαδικασία») αυτό γίνεται ορατή δήλωση για συνάδελφο. Αν πρέπει να
περιορίζεται σε διαχειριστές, είναι μία συνθήκη — αλλά είναι επιλογή
πολιτικής, όχι τεχνική.
