# docs/business-rules.md — Κανόνες Επιχειρησιακής Λογικής

> Τελευταία ενημέρωση: 2026-05-05
> Κάθε κανόνας έχει ID. Αναφέρετε πάντα το ID στον κώδικα.

## R1 — Μονοτονικότητα τιμών (Monotonicity)

**Κανόνας:** Σε κάθε zone, η τιμή ανά βάρος πρέπει να είναι
μεγαλύτερη ή ίση με την τιμή του προηγούμενου βάρους.

```
price[weight_n] >= price[weight_{n-1}]  για κάθε n
```

**Παράδειγμα παραβίασης:**
```
0.5kg = 8.50€  ✅
1.0kg = 8.49€  ❌ — ΑΠΑΓΟΡΕΥΕΤΑΙ
```

**Εφαρμογή:** Σε ΟΛΕΣ τις zones, όχι μόνο Z1.
**Έλεγχος Z7 πρώτα** — είναι η zone που σπάει πιο εύκολα.
**Πηγή:** R-Excel-1 στο CLAUDE.md

---

## R2 — Versioning Tariff (Εκδόσεις Τιμοκαταλόγου)

**Κανόνας:** Κάθε νέος χρόνος = νέο `Tariff` record με νέο `valid_from`.
Ποτέ δεν τροποποιούνται οι τιμές ενεργού tariff.

**Παράδειγμα:**
```
DHL 2025: valid_from=2025-01-01, valid_to=2025-12-31
DHL 2026: valid_from=2026-01-01, valid_to=null  ← ενεργό
```

**Πηγή:** R-Excel-4 στο CLAUDE.md

---

## R3 — Λογική Slab Rate (Cumulative)

**Κανόνας:** Το `Rate` στο CMS import είναι η **διαφορά** (incremental)
μεταξύ συνεχόμενων τιμών — ΟΧΙ η συνολική τιμή.

```
Rate[bracket_n] = price[weight_n] - price[weight_{n-1}]
```

Η συνολική τιμή για ένα βάρος = SUM όλων των Rate μέχρι εκείνο το bracket.

**Πηγή:** docs/cms-import-format.md §3

---

## R4 — UptoWeight Συμπύκνωση

**Κανόνας:** Όταν συνεχόμενα brackets έχουν το ίδιο Rate,
συμπτύσσονται σε μία γραμμή με `UptoWeight` = τελευταίο ToWeight της ομάδας.

**Πηγή:** docs/cms-import-format.md §4

## R5 — DOCS vs NON_DOCS

**Κανόνας:** Κάθε service εισάγεται στο CMS δύο φορές:
μία ως `docs` και μία ως `non docs`.

Για DHL 2026: οι τιμές DOCS και NON_DOCS είναι **ίδιες**.
Εισάγονται και οι δύο για μελλοντική ευελιξία (μπορεί να αλλάξουν σε επόμενο έτος).

---

## R6 — Προσαύξηση (Markup) Γνωστοποίησης Τιμών

**Κανόνας:** Το CMS import για γνωστοποίηση τιμών πελάτη
παράγεται από τον raw DHL tariff + ποσοστό προσαύξησης.

```
price_client[weight] = price_dhl[weight] × (1 + markup_pct / 100)
```

**Προσαύξηση ορίζεται ανά service** (όχι ανά zone ή βάρος).

**Παράδειγμα:**
```
S1003 markup = 180%
DHL Z1 0.5kg = 8.48€
Τιμή πελάτη  = 8.48 × 2.80 = 23.74€  (στρογγυλοποίηση 2 δεκαδικά)
```

## R7 — Envelope (Φάκελος έως 300g)

**Κανόνας:** Το bracket Envelope (0.3kg) του DHL **δεν χρησιμοποιείται**.
Η 4A Express δεν πουλά αυτή την υπηρεσία.
Ο τιμοκατάλογος ξεκινά από **0.5kg**.

## R12 — Σειρά Εφαρμογής Markup στο CMS Import (ΚΡΙΣΙΜΟ)

**Κανόνας:** Το markup εφαρμόζεται στο **incremental rate** (διαφορά τιμών),
ΟΧΙ στις flat τιμές.

**Λάθος ροή (προκαλεί εναλλαγή 2.96/2.97):**
```
flat_price[n] × (1 + markup)  →  diff(marked_flat[n], marked_flat[n-1])  →  Rate
```

**Σωστή ροή:**
```
diff(flat[n], flat[n-1])  →  raw_rate  →  raw_rate × (1 + markup)  →  Rate
```

**Παράδειγμα Z1 S1003, markup 180%:**
```
DHL raw rate 10.1-20kg = 1.06€ per 0.5kg
1.06 × 2.80 = 2.968 → στρογγυλοποίηση = 2.97 (πάντα σταθερό)

Αν markup στη flat τιμή:
  marked[10.5] = 29.80 × 2.80 = 83.44
  marked[11.0] = 30.86 × 2.80 = 86.41
  diff = 86.41 - 83.44 = 2.97 ✅ (τυχαία)
  marked[12.0] = 32.98 × 2.80 = 92.34
  marked[11.5] = 31.92 × 2.80 = 89.38 (στρογγυλοποίηση!)
  diff = 92.34 - 89.38 = 2.96 ❌ (λόγω σωρευτικής στρογγυλοποίησης)
```

**Αποτέλεσμα σωστής ροής:** Σταθερό rate → μέγιστη συμπύκνωση brackets.
Λάθος ροή: εναλλαγή 2.96/2.97 → αδυναμία συμπύκνωσης → 35× περισσότερες εγγραφές.

**Πηγή:** Phase 3a — generate_cms_import.py

## R13 — Αυτόματη Ενημέρωση Επίναυλου Καυσίμων (ΠΡΟΑΠΑΙΤΟΥΜΕΝΟ)

**Κανόνας:** Ο επίναυλος καυσίμων είναι **εβδομαδιαίος** (κάθε Δευτέρα).
Το σύστημα ΔΕΝ επιτρέπει χειροκίνητη εισαγωγή επίναυλου.
Η ενημέρωση γίνεται **αυτόματα** μέσω Claude API που διαβάζει το DHL site.

**Ροή:**
```
Κάθε Δευτέρα (ή κατ' απαίτηση):
  Claude API → διαβάζει mydhl.express.dhl → επιστρέφει τιμές
        ↓
  Dashboard ενημερώνεται αυτόματα
        ↓
  Αν άλλαξε vs προηγούμενη εβδομάδα → ειδοποίηση
```

**Γιατί είναι προαπαίτημενο:**
- Λανθασμένος επίναυλος → λάθος κόστος → λάθος κέρδος στο tooltip
- Ο χρήστης δεν πρέπει να θυμάται να ενημερώνει χειροκίνητα

**Πηγή:** mydhl.express.dhl/gr/el/ship/surcharges.html#/fuel_surcharge
**Υπεύθυνος:** Claude API (web_search + web_fetch)

## R14 — `type` ≠ `fuel_type` (τρόπος μεταφοράς έναντι τύπου επίναυλου)

**Κανόνας:** Στον `4a_services` συνυπάρχουν δύο στήλες με διαφορετική σημασία
και **δεν πρέπει να συγχέονται**:

- **`type`** — ο *τρόπος μεταφοράς* της υπηρεσίας: `AIR`, `ROAD`, `SEA`, `COMBI`.
- **`fuel_type`** — *ποιος επίναυλος εφαρμόζεται*: `AIR`, `ROAD`, `AIR_CY`,
  `NONE`, ή `NULL` αποκλειστικά για τις `COMBI`. Το λεξιλόγιο ζει στον
  `4a_fuel_types`, με `source` (ποια τιμή του cache διαβάζεται) και
  `multiplier`.

**Για τις COMBI διαφέρουν σκόπιμα.** Η `S1050` μεταφέρει συνδυασμένα,
αεροπορικά και οδικά, άρα `type = COMBI`. Ο επίναυλός της όμως είναι `ROAD`,
γιατί χρεώνεται με βάση το σκέλος Ελλάδα↔κόσμος. Επιβεβαιώθηκε στο CMS στις
07-10-2026: `S1050` και `S1051` με 40%.

**Επίλυση με κανόνα, όχι με λίστα κωδικών.** Οι COMBI κρατούν `fuel_type NULL`
και ο τύπος τους προκύπτει από την υπηρεσία που δείχνει το `tariff_source`
(`S1050 → S1010`, `S1051 → S1041`). Η επίλυση ζει **μόνο** στο view
`v_services_fuel`:

```sql
COALESCE(s.fuel_type, src.fuel_type) AS fuel_type
FROM 4a_services s
LEFT JOIN 4a_services src ON src.code = s.tariff_source
                         AND src.code <> s.code
                         AND src.type <> 'COMBI'
```

Έτσι, αν αλλάξει ο τύπος της βάσης υπηρεσίας, η COMBI ακολουθεί αυτόματα.
Καμία αποθηκευμένη αντιγραφή που μπορεί να παλιώσει.

**Γιατί πρώτο το ρητό:** οι παραλλαγές `_GR`/`_CY` έχουν `tariff_source`
`S1003`/`S1012`, που είναι `AIR`. Αν η επίλυση κληρονομούσε πάντα από το
`tariff_source`, θα έπαιρναν λάθος `AIR` αντί `NONE`. Το `COALESCE` βάζει
πρώτη τη ρητή τιμή και το `NULL` μένει μόνο για τις COMBI.

**Φύλακες (τεστ συνέπειας, όχι σιωπηλό NULL):**
- μη-COMBI με `fuel_type IS NULL` → σφάλμα
- COMBI χωρίς `tariff_source`, ή με `tariff_source` που είναι κι αυτό COMBI → σφάλμα
- καθολικά: κανένα επιλυμένο `fuel_type` δεν επιτρέπεται να είναι `NULL`

**Στρογγυλοποίηση:** η τιμή ανά τύπο υπολογίζεται σε **ένα σημείο, στον
server**: `pct = round_half_up(source_pct × multiplier, 2)`, με **bcmath**
και όχι float — το `46.25 × 1.06 = 49.025` είναι περίπτωση `.xx5` σε
μη-δυαδικό κλάσμα και η float στρογγυλοποίηση είναι επισφαλής. Το frontend
**δεν ξαναϋπολογίζει**, μόνο εμφανίζει.

**Πηγή:** `db/migrations/2026-10-07a_fuel_types.sql`,
`db/migrations/2026-10-07b_services_fuel_type.sql`

## R15 — Οι ζώνες του αρχείου CMS έχουν μία και μόνη πηγή

**Κανόνας:** Οι ζώνες κάθε γραμμής του αρχείου CMS προέρχονται **ΜΟΝΟ** από
το `4a_fuel_cms_services.zones`. **Ποτέ** από το `4a_services.zone_list`.

**Γιατί:** οι δύο κατάλογοι αποκλίνουν σκόπιμα και νόμιμα.

- Το `4a_services` περιγράφει **τις υπηρεσίες που τιμολογούμε**. Οι ζώνες του
  φτάνουν μέχρι `z7` (και `z9` για Κύπρο).
- Το `4a_fuel_cms_services` περιγράφει **τις γραμμές που δέχεται το CMS**.
  Περιέχει ζώνη **`Z10`** (στις `S1003`, `S1029`, `S1032` σταθμού GR) και
  τέσσερις υπηρεσίες που **δεν υπάρχουν καθόλου** στο `4a_services`:
  `S1026`, `S1027`, `S1029`, `S1032`.

Αν η παραγωγή διάβαζε ζώνες από το `4a_services.zone_list`, θα έχανε σιωπηλά
τη `Z10` και θα απέτυχε εντελώς στις τέσσερις υπηρεσίες που ζουν μόνο στο CMS.
Το αρχείο θα έβγαινε με λιγότερες γραμμές από όσες περιμένει το CMS, χωρίς
κανένα σφάλμα.

**Το αντίστροφο επίσης:** το `4a_fuel_cms_services` κρατά δικό του
`service_name` και δικό του `fuel_type` και **δεν κάνει join** στις
υπηρεσίες. Το τεστ συνέπειας (R14) ελέγχει μόνο τους **κοινούς** κωδικούς,
σήμερα 8 από 12.

**Πηγή:** `db/migrations/2026-10-07c_fuel_cms_catalog.sql`,
`fuel_cms_rows()` στο `api/fuel_lib.php`
